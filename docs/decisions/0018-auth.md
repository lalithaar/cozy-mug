# 0018 — optional auth identity layer

- Status: firm (implemented)
- Date: 2026-10-13
- Supersedes: 0012 (data access context only; auth nutrient)

## Opinion
`auth` is an opt-in behavior package layered over `session` and `data`. It owns
password hashing, login/logout, current-user resolution, and route guards. It
does **not** own the User model: apps define their own model via `data.Model`
and pass a loader to resolve it. The default password hasher is
`PBKDF2-SHA256` via stdlib `crypto/pbkdf2`; a `Hasher` interface allows apps
to supply bcrypt/argon2 without adding it to the framework.

## Because
Authentication is a nutrient we owe (0015), but owning the User schema would
conflict with cozy-mug's model-first declaration (0016) and would force fields
(approval, role, etc.) apps may not want. A behavior layer plus app-owned
models keeps the framework small and the app sovereign over its identity data,
while still removing repeated security-sensitive boilerplate. PBKDF2 default
matches Django's default and costs zero new dependencies.

## Alternatives rejected
- Framework-owned `auth.User` model — rejected for model-first conflict.
- External `golang.org/x/crypto` as default — rejected because stdlib PBKDF2
  is sufficient by default; a dependency exception needs a stronger reason. The
  `Hasher` seam leaves that option to apps.
- Full auth subsystem with reset/mailer/rate limiting — rejected for v1; scope
  stays hashing + session identity + guards + loading.

## Apply when
Any SSR app needs login/logout, a current user, or protected routes.

## Deviate / ask when
A change would require a new security mechanism, mail, jobs, user management
surface, or a framework-owned user schema; make an ADR first.

## Revisit if
Evidence shows PBKDF2 parameters or the behavior-layer model do not meet app
needs across multiple real apps.
